= What upkeep is
:description: A reconciler for the cloud footprint of a website or SaaS app.

One file describes what an app's cloud footprint should be. `upkeep` reads what
it actually is, prints the difference, and — only if you ask — closes it.

[source,console]
----
$ upkeep plan
MANUAL  render-env  FEE_ACCOUNT_INFO      real bank details, shown to a customer verbatim
MANUAL  render-env  R2_SECRET_ACCESS_KEY  set $R2_SECRET_ACCESS_KEY locally, then re-run
CREATE  render-env  R2_BUCKET             not set on the service → my-bucket
UPDATE  r2-cors     my-bucket             no CORS rule at all, so a browser cannot upload

2 of these cannot be automated and are yours to do.
----

== Why it exists

The failure it was written after: an app shipped with none of its object-storage
variables set. Nothing errored. The service booted, served every page, and
answered `404` to one endpoint — photo upload — for days. Every layer reported
success, because from each layer's point of view nothing had gone wrong.

So `upkeep` has a fourth kind of action, `MANUAL`, for changes no tool can make.
An R2 API token cannot be minted from any CLI; real bank details are nobody's to
invent. A tool that could only automate would have reported that same clean
success.

TIP: Naming the gap is the feature. A converged plan that still lists manual
actions has not failed — it has told you the truth.

For the same reason, `apply` re-reads afterwards. A provider returning `200` is
not evidence a change took.

== What it manages

[cols="1,2,2"]
|===
| Surface | Reconciles | Reports only

| Render
| service environment, deploys
|

| Cloudflare R2
| bucket, public access, CORS
|

| Cloudflare Pages
| production branch
| domains it does not know about

| Neon
|
| branch exists, `DATABASE_URL` agreement
|===

It never deletes by omission: a variable the config does not name is left
exactly as it is. Dropping a database or repointing a live service at another
one are not things a config file should do quietly, so it does not.

Adding a provider is one package and one case. See xref:extending.adoc[].

== The auth surface

Every other surface checks one system against a config. `auth` checks several
variables against each other, because that is where authentication actually
fails: not a missing value, but two values that disagree — and nothing notices
until somebody tries to sign in.

It asserts, and proves what can be proved:

* the frontend and the service name the same provider (the frontend's is baked
  into its bundle, so it cannot be read back — declaring it is the only way)
* `AUTH_JWKS_URI` is fetched and actually serves keys, because a URL being set
  is not evidence it resolves
* the issuer serves this app's own keys, when the app signs its own tokens
* the session endpoint answers JSON rather than a 404 or a single-page app — a
  404 there reads exactly like "no session"
* `CORS_ORIGINS` contains every origin the site is served from, matched exactly
* `AUTH_DEV_BYPASS` is not true on a production service

It changes nothing. Authentication is the one surface where a wrong automatic
fix locks out everybody, including whoever ran the tool.

== Two hosting providers

`render` and `fly` are alternatives: declare one or the other. They share no
code, only an interface, which is what makes adding a third a package rather
than a refactor.

They differ in what they can honestly report, and the plans say so:

* Render returns a variable's value, so `upkeep` can tell you one *differs from
  the config*.
* Fly returns a secret's name and digest and never its value, so `upkeep` can
  tell you a secret is *missing* and can set one — but cannot tell you an
  existing one is wrong. It stays silent about those rather than claiming a
  comparison it did not make.
